# 性能实测

> 本文件是 [README](../README.md) 的分册；接口信息用 `go doc github.com/go-comm/ghromex/<包>` 查。

## 怎么量：`GHROMEX_BENCH=1`

主循环的各段（布局 / 清屏 / 重绘 / 呈现 / 空闲）**分开计时**，累积 ≥300 帧
（`GHROMEX_BENCH_FRAMES` 可调）后报 p50/p95/p99/**max**，并打印渲染路径
（driver 名、是否 dummy）。基准模式会**强制每帧重绘、且不进入空闲休眠**
（模拟持续动画）：静态页面平时不重绘、主循环还会 `Delay(10)` 省 CPU，那样量到
的只是空闲休眠，渲染管线的成本和 vsync 等待都测不到。

**max 不是可选的**：分位数会吞掉最要紧的那类缺陷——压力页上「开页后第一档滚轮
重排整棵树 1750ms」在 104 帧的批次里只占一个样本，p95/p99 读出来仍是 43/44ms
（看着正常），用户体感却是「每次打开页面后第一下滚轮卡住」。偶发的一次性尖峰只
有 max 能看见。

滚动期另有专项探针 `GHROMEX_SCROLLPROBE=1`（隐含 bench 的分段采集，另加
`TickScroll` 计时、绘制调用构成、布局取证、到界自动掉头，见
`browser/scrollprobe.go`）。它**注入真实滚轮事件**走 `onWheel → 滚动动画 →
TickScroll` 那条链，而不是人造的静止重绘——bench 的「强制每帧重绘」量到的是
「把当前这一屏重画一遍」，滚动专属的开销（`TickScroll` 平移子树、滚动到新位置
后可见集合变化）完全没进统计。用法与压力页生成器见下文[「大文档滚动：帧成本的构成」](#大文档滚动帧成本的构成与一次-175-秒的重排实测)：

```
go run ./examples/stressgen -out .temp/stress.html
go build -o .temp/browser.exe ./examples/browser
GHROMEX_SCROLLPROBE=1 GHROMEX_SCROLLPROBE_EVERY=8 GHROMEX_SCROLLPROBE_NOTCH=4 ^
  .temp\browser.exe -page .temp\stress.html -exit-after 40s
```

`EVERY=8 / NOTCH=4` 是接近真实设备的节奏：**每帧**注入会让滚动动画每帧被重定向
（`startScrollAnim` 清零动画时间），那一帧本就没有位移，量到的是「注入频率超过
真实设备」的失真数据。探针自带「到界自动掉头」（连续 4 次无位移就反向），并报
「有位移帧」比例——比例低说明页面不可滚或滚轮落在不可滚动元素上，这批数字按静止
页理解。

只做本地诊断，**不进 CI**：计时受机器负载、驱动、电源策略影响，数值不可
复现，写成断言只会得到 flaky 的测试。

## 口径（先说清楚，否则数字会打架）

| 段 | 软件路径（SDL 软件光栅器） | 加速路径（D3D11） |
|---|---|---|
| 重绘 | **只是命令入队**——SDL 把 DrawColor/DrawText 记进命令表 | 提交绘制命令给驱动 |
| 呈现 | 真正的像素填充 + 拷贝到窗口 | 交换链提交 + **等 vsync** |
| 空闲 | 正常运行时是 10ms 节流休眠，**不是** vsync；基准模式不睡（模拟持续动画） | 同左 |

两个关键差异：

1. **软件路径的「重绘」量到的不是光栅化**。像素填充发生在 Present 时——所以
   「清屏」看着是 0ms（填整块 viewport 也在 Present 里），而「呈现」随画布
   面积涨。这也是「纯绘制 1.5ms」与「整帧 4ms」能对上的原因：后者是两者之和。
2. **加速路径的「呈现」里混着「等 vsync」**（不阻塞就抢不到交换链）。bench
   会额外关一次 vsync 量出纯拷贝耗时，二者相减即等 vsync 的时间。实测
   **等 vsync 13.5~14.5ms、纯拷贝 0.3~1.1ms**——所以「GPU 整帧 16.6ms」里
   只有 1.3~3ms 是真实工作，其余基本是等显示器（见实测 A）。

## 实测 A：加速路径（D3D11，真实窗口，门户页，400 帧）

| 窗口 | 绘制调用/帧 | 重绘(提交) | 呈现 p50 | 其中等 vsync | 纯拷贝 | 帧周期 |
|---|---|---|---|---|---|---|
| 800×600 | 996 | 1.18ms | 14.74ms | 14.48ms | 0.27ms | 16.55ms |
| 1280×820 | 1194 | 1.32ms | 14.62ms | 14.05ms | 0.57ms | 16.47ms |
| 1920×1080 | 1549 | 1.56ms | 14.80ms | 13.77ms | 1.02ms | 16.61ms |
| 2560×1440 | 2026 | 1.91ms | 14.56ms | 13.46ms | 1.10ms | 16.59ms |

读法：**GPU 每帧真实工作只有 1.3~3ms**（重绘提交 + 纯拷贝），其余 13.5~14.5ms
是等 vsync——这就是「16.6ms 的整帧」的真面目：等待，不是工作。工作量越大等得
越少（总量恒定在 16.6ms）。4K 与 800×600 的重绘只差 0.7ms，填充完全不成问题。

（静态页面不重绘时，主循环会 `Delay(10)` 省 CPU，此时 Present 只等剩余几毫秒，
帧率仍是 60fps；bench 模拟的是持续动画，等待才会完整暴露。两种情形都说明
「16.6ms」不能当 GPU 的工作量。）

## 实测 B：软件路径（SDL 软件光栅器，dummy 驱动，门户页，400 帧）

| 窗口 | 绘制调用/帧 | 入队(重绘) p50 | 填充+拷贝(呈现) p50 | 帧周期 | 每帧分配 | 堆常驻 |
|---|---|---|---|---|---|---|
| 800×600 | 996 | 1.01ms | 1.10ms | 2.06ms | 214KB | 3.1MB |
| 1280×820 | 1194 | 1.20ms | 1.90ms | 3.04ms | 239KB | 3.1MB |
| 1920×1080 | 1549 | 1.40ms | 3.45ms | 4.86ms | 273KB | 3.3MB |
| 2560×1440 | 2026 | 1.80ms | 4.40ms | 6.24ms | 326KB | 3.3MB |

（堆常驻是 GC 后的读数，**量级参考**；每帧分配是 Go 侧累计分配，原生侧——
纹理、目标缓冲——不在其中。帧周期 = 入队 + 呈现，逐行都对得上。）

## 软件路径的 4K 下限：一次躲不掉的 blit（实测）

「呈现」里到底有多少是填充、多少是拷贝？用**空 Present**（画完一次就反复
Present、中间不画任何东西）就能把这部分单独量出来——空 Present 里没有任何
待光栅化的命令，量到的就是「把窗口表面交给显示」的代价：

| 窗口 | 空 Present | 整屏填充 + Present | 填充本身 |
|---|---|---|---|
| 1280×820（4.0MB） | 1.46ms | 1.48ms | 0.02ms |
| 2560×1440（14.1MB） | 2.09ms | 2.45ms | 0.34ms |

（`SDL_VIDEO_DRIVER=dummy` 下量到 1.47 / 2.26ms，与真实窗口几乎一样——
这笔开销不取决于有没有显示器，就是一次整屏像素传递。4K 整屏填充只要
~0.3ms：不透明纯色走 `memset`，约 40GB/s。）

**结论：4K 下 2.4ms 的帧里，2.1ms（86%）是那次整屏 blit，与页面内容无关。**
所以软件路径在 4K 的帧时间下限就在 2ms 量级——填充再省也压不下去。

顺带排除了一个想当然的优化（**已实测否掉、代码已撤**）：以为把软件渲染器
直接建在窗口表面上（`SDL_CreateSoftwareRenderer(SDL_GetWindowSurface())`）能
省掉 SDL 内部的一次全屏拷贝，预计 4K 砍 1~2ms。实测「空 Present」1.43ms /
2.03ms，与默认路径（1.46 / 2.09ms）在噪声内，帧时间也一样——**没有第二次
拷贝可省**：SDL 的软件渲染器本来就画在窗口表面上，上面那 2.1ms 就是它把
窗口表面交给显示的那一次，躲不掉。（这条路径唯一的可见差异是填充改为即时
执行而非排队到 Present，总量不变。）

## 大文档滚动：帧成本的构成，与一次 1.75 秒的重排（实测）

压力页口径：14.9MB HTML / 约 42 万元素、1024×720、软件渲染器、
`SDL_VIDEO_DRIVER=dummy`、持续注入滚轮（`GHROMEX_SCROLLPROBE=1`，见下）。
对照页是门户页（约 3k 节点），同一台机器同一口径：

| 段 | 压力页 p50 | 门户页 p50 |
|---|---|---|
| 滚动平移（`TickScroll`，每帧） | **107ms** | ~0ms |
| 重绘（命令入队，每帧） | **198ms** | 1.00ms |
| 呈现（填充 + 拷贝） | 1.00ms | 1.55ms |
| 绘制调用/帧 | 981（文字 816 / 色块 109） | 1183（文字 433 / 色块 334） |
| 每帧分配 / 堆常驻 | 89.8MB / 755MB | 277KB / 2.5MB |
| 有位移帧 | 93%（掉头 0 次） | 70% |

读法：两页的绘制调用数同量级（981 vs 1183），重绘却差 **198 倍**——耗时随
**节点总数**线性，不随调用数；视口裁剪是生效的（压力页文字片段数随滚动位置
在 691~866 波动，不随页高增长）。所以要省的不是「画多少」，而是每帧两次**全树
遍历**：`TickScroll` 107ms + `RenderNode` 198ms。折算到历史记录里那个 14.9 万
节点的页面约 (107+198)×149/420 ≈ 108ms，与当时记的「滚动帧 ~100ms」对得上——
口径自洽，探针可信。

（针对这两次遍历有过一版「滚动偏移改绘制/命中期现算」的完整设计，评估后
**封存**：它只消掉平移 107ms + 快路径 40ms，重绘遍历 198ms 分文未动，而坐标
语义改动对 ui/事件/宿主是高风险连锁。设计、封存理由与重启条件见
[rfc/0001-scroll-offset-propagation.md](rfc/0001-scroll-offset-propagation.md)。）

## 修过的一处：开页后第一档滚轮重排整棵树（1750ms）

`LayoutDocument` 收尾时先写 `lastLayoutChange = changed`、再同步视口尺寸；
视口尺寸从 0 变成实际值时补的那一笔 `markChanged` 落在记账**之后**，使
`changed` 永久比 `lastLayoutChange` 多 1。而滚动快路径的判据正是「changed 与
scrollMark 的增量相等」，于是开页后（以及每次窗口缩放后）的第一档滚轮被判成
非滚动变更，走全量级联 + 布局。压力页实测（整树 13,380,022 次文本测量）：

| | 修前 | 修后 |
|---|---|---|
| 开页后第一档滚轮的布局 | **1750ms** | **40.4ms**（纯平移，测量 0 次） |
| 缩放后第一档滚轮的布局 | **1750ms** | 41.5ms |
| 缩放本身的布局 | 1750ms 全量一次 | 1750ms 全量一次（不变） |

修法：尺寸比对挪到判据**之前**并作为快路径否决项（平移改不了盒宽），尺寸变更
只发 `onChanged` 回调、不再加变更计数（本次布局已用新尺寸消化掉）。复测滚动期
13 次布局全是 43ms 纯平移，唯一的全量重排落在首帧——那是开页后往文档里装工作
台 chrome 触发的启动代价（另计，见 [CHANGELOG.md](../CHANGELOG.md)）。

回归见 `engine/scroll_layout_internal_test.go`，判据用**文本测量次数**而非计时
（快路径 0 次、全量整树）：开页后滚轮 / 缩放后滚轮必须纯平移、带滚动的缩放必须
全量、动画帧不得混入非滚动变更。修复前前三条全部失败。

## 修过的一处：悬停/按下/焦点一律全量重排（1.72s → 零重排）

滚动之外的另一处同类缺陷：`SetHoveredElement` / `SetActiveElement` /
`SetFocusedElement` 变化时一律 `markChanged` → 主循环全量级联 + 布局。鼠标
滑过一个元素就是 1.7 秒（同上压力页），而这些变更里绝大多数**只改颜色**——
盒模型一个像素都不动；无 `:hover` 规则的页面更是连样式都不变，1.7 秒什么都没
买到。

现在按**变更档位**分级（`engine/change_level.go` / `hover_change.go`）：

1. 没有任何受影响的元素（规则不提及该状态、也不在表单控件上）→ 零标记零通知；
2. 状态规则的声明全是纯绘制属性（颜色/背景/`-color` 族等白名单）→ 就地重算
   受影响子树的样式 + 记**重绘账**（`PaintCount`），主循环跳过布局直接重绘；
3. 规则可能改盒模型（padding/width/font-…）→ 照旧全量重排（白名单判错的方向
   只会是多排一次，不会漏排）。

三档同口径实测（压力页 14.9MB / 约 42 万元素，`stressgen -hover` 生成变体）：

| 页面变体（悬停中部 section） | 档位 | 引擎侧耗时 | 修前 |
|---|---|---|---|
| 无 `:hover` 规则（默认） | None | **1.0ms**（binder 扫描），零标记 | 1.72s 全量重排 |
| `section:hover{background:…}` | PaintOnly | **<1ms**，样式就地生效 | 1.72s 全量重排 |
| `section:hover{padding:…}` | Reflow | 1.78s 全量（回退基线，不变） | 1.78s |

PaintOnly 档的正确性靠两件事钉住：样式在**标记前**就地级联（下一帧即便走滚动
快路径跳过级联，悬停颜色也不回退）；paint 账不进 changed/scrollMark 两本账
（滚动快路径的「增量相等」判据不受污染，悬停后下一档滚轮照旧 40ms 纯平移）。
回归见 `engine/hover_change_internal_test.go`（档位契约 / 级联范围哨兵 /
滚动快路径不被污染等 9 条，判据同为文本测量次数与账本增量）。

## 怎么读这些数

- **入队时间随绘制调用数涨**：调用 ×2.03 ↔ 入队 ×1.78——同向，但不是严格
  线性（遍历、盒模型裁剪等固定开销随尺寸变了）。
- **「呈现」时间随画布面积涨**：面积 ×7.7 ↔ 呈现 ×4.0（亚线性——拷贝与填充
  都随面积，固定开销占比随面积下降）。两者拆不开，这也是没法把它单独归给
  「填充率」的原因——**空 Present 的实测**（上一节）显示其中大头是那次必备的
  整屏 blit（4K 约 2.1ms），不是我们的填充。
- 两条都在涨，但都**远低于** 60fps 的 16.6ms 预算。所以这里**不必归因到
  单一瓶颈**：调用数与面积都在涨，各自都还够用。要定位时看哪一条更陡。
- **两条路径不能按「整帧」横比**。加速路径的 16.6ms 是「锁帧周期」，软件路径
  没有 vsync、按工作量跑。要比就比 **CPU 侧真实工作**：GPU 1.3~3ms（命令
  提交 + 纯拷贝，填充在 GPU 上异步完成、不占 CPU）vs 软件 2.1~6.2ms（入队 +
  填充/拷贝全在 CPU 上），同量级；差距只在 4K 且内容更重时才会拉开。
- 之前记录的「2560×1440 整帧 4.07ms」= 入队 + 呈现，与这里的
  1.80 + 4.40 ≈ 6.2ms 量级一致 ✓（机器与采样细节不同）。而「纯绘制 1.5ms」
  那个数**只量到入队**，口径不同，不能与整帧数并排。

## 大文档的每节点成本：字段排布即内存

样式与布局缓存都挂在节点上，于是**每个节点结构体的大小直接乘进常驻内存**。
一页 714KB 的 API 参考（27,501 元素 + 37,579 文本节点 = 65,080 节点）实测：

| 结构体 | 重排前 | 重排后 | 省下 |
|---|---|---|---|
| `htmlElement`（66 字段） | 680B | **624B** | 3.5 MB |
| `cssStyleDeclaration`（44 字段 + 内嵌接口） | 440B | **400B** | 2.5 MB |

文档常驻堆 **81.3 MB → 75.3 MB（−6.0 MB，−7.4%）**，整轮解析+级联+布局+绘制
耗时持平（134.0 → 131.4 ms）。没有任何逻辑分支改动，只是把字段按三段落位：

1. **含指针段**（接口 / 指针 / 切片 / map / string / func）——`Size`/`Rect`/`Color`
   都是接口，所以样式字段大多落在这里；
2. **纯数值段**（int / int64 / float32 / float64 / 数组）——Go 的指针扫描按
   `ptrdata` 收尾，这段整洁排列后 GC 不必再逐字判断；
3. **单字节段**（bool 与枚举）——原先 14 个 bool 散在对齐字段之间，**每个都撑出
   5~7B 空洞**（58B，占 8.5%），聚到一起后互相填满。

`engine/field_packing_internal_test.go` 钉住了两条不变量：尺寸不得回涨、含指针
字段不得出现在纯数值字段之后。新增字段时据此归位即可。

（后来 textarea 的折行缓存又往含指针段加了 1 个指针字段，`htmlElement` 现为
**632B**——测试里的期望值同步为 632。分段与空洞两条不变量不受影响，多出的
8B 是一个指针，落在第一段。增量布局阶段一再加 `lcache *layoutCache`（布局缓冲
缓存）指针字段，现为 **640B**，测试同步为 640，同样落在含指针段、不产生空洞。）

> 顺带记录一个被数据否掉的想法：把这些低频字段（滚动动画 130B、生成盒 50B、
> 控件 27B）改成按需 side table，按真实占比只能省 203B/节点、约 12.6 MB，却要动
> 164 处调用点，还要为每个条目管生命周期。纯重排拿到 6 MB、零调用点改动，收益
> 成本比高得多。

## 文本节点不各持一份样式：共享父元素的 computed

一页 714KB 的 API 参考有 **27,501 元素 + 37,579 文本节点 = 65,080 节点**，
文本节点占 57.7%。若每个文本节点也独立级联，就要多付 37,579 × 400B ≈
**14.4 MB** 样式对象，外加上万条规则的匹配时间——而文本在真实 DOM 里**不是
元素**，选择器根本匹配不到它。

因此级联时文本节点直接将父元素的 computed 指针赋给自己（与 `::before`/
`::after` 的文本盒同法）：文本会读的 `color`/`font-size`/`font-family`/
`font-weight`/`line-height`/`text-decoration`/`visibility` 全是**继承**属性，
与父元素等值，共享即等价复用：

| | 共享前 | 共享后 |
|---|---|---|
| 每文本节点样式对象 | 1 份 400B | 0（指父元素那份） |
| 独立对象数（实测） | 37,579 | **0** |
| 文档常驻堆 | 74.6 MB | **59.4 MB**（−15.2 MB，−20.4%） |
| 整轮 解析+级联+布局+绘制 | 132.0 ms | **101.2 ms** |

叠加前面那次字段重排，同一页从 **81.3 MB 降到 59.4 MB（累计 −27%）**。
（表里「共享前」74.6 MB 与上一节的 75.3 MB 是同口径两次独立测量，运行间噪声
约 1%；同一次对照测量给出的差值是 −15.2 MB。）

**代价与守卫**：共享对象带着父元素的**非继承**属性（display/position/
padding/opacity/overflow…），所以凡是「拿 computed 判盒」的地方都必须把
文本节点排除在外，共 5 处——`isPositioned`（定位层收集）、`layoutPositioned`
（第二遍定位)、`shiftBox` 的 fixed 跳过、`renderNodeTextColor` 的 opacity
包裹、`GetBoundingClientRect`（零盒口径）。这 5 处**不是给文本开的特例分支，
而是文本本来就没有盒**：排除之后行为与共享前逐像素一致。

判定统一走 `htmlElement.isText()`（看 `nodeType` 字段），**不比较标签名字符
串 `"#text"`**：节点类型是类型信息，寄存到名字里则拼错一个字符编译期也拦不
住，且会误伤「标签名恰好等于 `#text`」的元素。`"#text"` 只保留在 `TagName()`
/ 序列化这类展示口径上。`engine/cascade_text_share_internal_test.go` 逐条钉住
这 5 处守卫，另有一条用例锁定 `:hover` 纯绘制档下文本跟随父元素换色的交叉
行为（共享对象就地改写，级联不得换新对象，否则文本会停在旧颜色）。

## textarea 不重复折行：折行结果挂在元素上

`layoutTextarea` 一帧内会被上溯 **约 8 次**（绘制、选区矩形、光标↔坐标映射、
滚动条几何、滚动夹紧、SVG 导出…）。旧实现每次调用都从头贪心折行全文：`[]rune`
一次 80MB、逐字 `string(r)` 2000 万次、每行再 `string(cur)` 复制一份。

19.5MB 的 `LICENSES.chromium.html`（360,214 行）塞进一个 textarea，1024×720 无头
视口，纯引擎探针实测：

| 指标 | 修复前 | 第一阶段（折行缓存） | 第二阶段（输入路径 byte 化） |
|---|---|---|---|
| 首帧总分配 | **1,358 MB** | **119 MB** | 142 MB |
| 后续 5 帧累计分配 | 6,497 MB（≈1.3 GB/帧） | — | — |
| 后续 50 帧累计分配 | 63.5 GB（按 1.3 GB/帧 推算） | **504 KB**（≈10 KB/帧） | 同左 |
| 常驻堆（文档 + 缓存） | ~400 MB | **105 MB** | **36 MB** |
| 单键（输入 1 字 + 重排 + 绘制） | — | **145 ms / 235 MB** | **71 ms / 103 MB** |
| 连敲 10 字后 `Sys` | — | 435 MB | **112 MB** |

三处改动，彼此正交：

1. **折行缓存** `htmlElement.wrap *textareaWrap`：键是「值 + 可用宽 + 字体 +
   度量后端」。值变化由 `SetAttribute("value")`/`RemoveAttribute` 把缓存置 `nil`
   失效，宽度/字体变化在取用时比签名。
2. **行只存下标**（`{start,end,bstart,bend,w}`：rune 区间 + 字节区间），行文本按
   字节区间现切——绘制/导出时才落成 string。行区间不存文本副本，19.5MB 的值
   不再被复制 8×。
3. **逐字宽度备忘**：ASCII 走 128 元素定长数组、其余走 map，度量次数从
   「字符总数」降到「不同字符数」。

## 大文档的行遍历只做两次定位

折行结果可达百万行（19.5MB 文本 900px 宽下 ~24 万行），而同屏可见的只有十几行，
每行遍历全表是纯浪费。三处消费点都改成 O(log n) 或 O(1) 定位：

| 位置 | 改动 |
|---|---|
| `caretRow`（光标↔行） | 线性扫描 → **二分**（行 `end` 单调） |
| 绘制 / 选区矩形 / SVG 导出 | 全表遍历 + 逐行判盒 → `visibleRows` **除法定位**首尾行 |

判定用**回归测试**而非计时（`textarea_wrap_cache_internal_test.go`）：断言二次布局的
文本测量次数掉到与文本长度无关的常数，且值/宽度变化会让缓存正确失效。测的是
「折行只发生一次」这个不变量——缓存一旦失效，行为仍然正确，只是每帧重新折行
全文，所以光看输出对不出来。

代价与守卫：缓存把值的 rune 视图（80MB）从「每帧临时」变成「常驻」，这是
105MB 常驻里的大头（值 19.5MB + runes 80MB + 行表 5.5MB）。行高/字体变化必须
进签名，否则用新字体画旧行宽；SVG 导出的 `Graphics` 与真实后端不同，也参与比较。

## 输入路径 byte 化：编辑不再转 `[]rune`

第一阶段把「打开文档」的常驻内存压下来了，但**敲一个字**仍是 145ms / 235MB：
编辑点 `insertTextAtCaret` 与 Backspace/Delete/Enter 六处都在 rune 空间拼接——
`[]rune(value)` 一次 80MB，`string(r[:c])+s+string(r[c:])` 再复制 117MB。改为
字节空间直接拼接（`value[:blo]+s+value[bhi:]`，实测 1.3ms / 19.5MB）后，单键
降到 **71ms / 103MB**，常驻再降到 **36MB**（80MB 的常驻 rune 视图彻底没了）：

- `textareaWrap.runes []rune` → `value string` + `n int`（末行 end）+ `exact bool`
  （值未因非法 UTF-8 被改写）；`textareaLine` 增 `bstart/bend` 字节区间，rune
  区间 `start/end` 口径不变（光标/选区/点击映射仍活在 rune 空间）。
- `lineText` 返回 `value[bstart:bend]` 子串（零拷贝），不再先 materialize 整篇
  `[]rune`。后端两个按字符串建键的缓存（`measureKey`/`texKey`）会多留一会儿旧值
  的底层数组，但键只比内容、且再跑一遍全文（24 万行）就随缓存整体清空，不累积。
- `runeByteIndex`/`byteIndexOf` 做 rune↔字节换算：以行表为锚二分定行 + 行内 walk
  （一行最多几百 rune），纯 ASCII 一步一字节不碰 `DecodeRune`。
- `wrapTextarea` 吃 string（ASCII 快路径逐字节走，同时记 rune/字节区间），CRLF
  仍两字节一起消费、行文本收在 `\r` 之前；`wrapTextareaInto` 复用预分配行表容量
  （24 万行 append 翻倍白扔约 10MB），行表每次新建防 `onChanged`→Refresh 重入
  改花旧布局。
- 非法 UTF-8 在 layout 时一次性 `string([]rune(value))` 消毒（保持旧 U+FFFD 口径），
  记 `exact=false`，编辑路径据此回退旧的 `[]rune` 拼接。

剩下的 71ms/键 是**每次编辑都要全量重折行**（值变了 → 缓存失效 → 下次布局从头
折 19.5MB）。这属于「增量折行」范畴，不在本次范围；本次只把「一次重折行」和
「一次编辑」本身的常数因子压下来。

## input / select 的可见窗口：从 O(n²) 到 O(n)

同一类坑在其它控件里也有，且更糟——`inputVisibleWindow` 与 `selectDisplayClipped`
判「舍到哪」时，**每舍掉一个字符就把剩下的整串重新量一遍**，2 倍长度 → 4 倍
开销；`input` 还在渲染路径里每帧无条件 `[]rune(displayValue)`。日常值很短所以
没暴露，长值直接卡死（19MB 的 `input` value 首帧 15 分钟没跑完）。

| 场景（1024×720 无头视口，稳定帧 `RenderNode`） | 修复前 | 修复后 |
|---|---|---|
| `input` 5,000 字符 | 54 ms / 12.9 MB / 帧 | **0.05 ms / 0.003 MB** |
| `input` 10,000 字符 | 213 ms / 50.8 MB / 帧 | **0.10 ms / 0.003 MB** |
| `input` 20,000 字符 | 860 ms / 201 MB / 帧 | **0.16 ms / 0.003 MB** |
| `input` 1,000,000 字符 | O(n²)，跑不完 | **7.5 ms / 0.003 MB** |
| `select` 1,000 字符 option | 2.5 ms / 0.51 MB / 帧 | **<0.01 ms / 0.001 MB** |
| `select` 4,000 字符 option | 33.9 ms / 8.17 MB / 帧 | **<0.01 ms / 0.004 MB** |
| `select` 200,000 字符 option | O(n²)，跑不完 | **0.33 ms / 0.20 MB** |

三处改动：

1. **字节游标 + 单字宽累加**（`inputVisibleWindow`）：不再 materialize `[]rune`，
   也不用「丢一字重测整串」。判据与旧实现逐字一致（累计单字宽 ≤ target 的最长
   前缀、至少留最后一个 rune、单字宽 ≤0 立即停），单字宽按 rune 缓存，度量次数
   只与「不同字符数」有关；窗口宽只在循环结束后量一次。`cut` 仍是 rune 下标。
2. **`clipTailToWidth`**（select 截断与 SVG 导出的输入尾部截断共用）：指数探测
   出超限位置后在小窗口内二分，度量次数 O(log 可见字符数)，与整串长度无关。
3. **去掉每帧全文 `[]rune`**：光标前缀与选区矩形都改按 rune 边界切字节
   （`runeByteIndex`），非法 UTF-8 只在入口消毒一次。

正确性用「新旧实现逐项比对」的随机化用例钉住（4,000 组 input / 3,000 组
select，含 CJK、组合附加符、非法 UTF-8、password/button、负宽度与各种
`textScrollSet` 状态，比 `text`/`cut`/`tw`/`th` 与截断结果），并用
`examples/ua`、`examples/notepad` 的 `-dump-svg` 与上一提交做 SHA256 逐字节比对。


## 布局缓冲跨轮复用（阶段一）：稳定态重排分配 1.76GB → 36MB

前面几阶段把「打开文档」「敲一个字」的常驻内存压下来了，但**稳定态全量重排**
（悬停、焦点、`ChangeCount` 驱动的任何一次 `LayoutDocument`）仍然是重灾区：
19.5MB 的 `LICENSES.chromium.html`（780 个 `<pre>`）一次重排实测 **503ms /
1.76GB 分配**，CPU 的 60% 花在 `runtime.scanObject`（GC 扫 runs 指针）。

根因：`layoutChildren` 每轮都**从零重建所有布局结果**——往 `node.runs` 逐个
`append textRun`（每 token 一项，全页约 450 万项、56B/项 ≈ 250MB），切片每轮
从 `nil` 按 1.25× 重新 grow，累计分配约 5 倍终值；行盒累加缓冲 `curLine`
同理（长 `<pre>` 单行几十万项）；`hasTrailingBlank` 每节点每轮把整串转成
`[]rune` 取尾（19.5MB → 一次 78MB 临时切片）。runs 是**布局结果**，该占的内存
必须占；不该占的是「每轮重新分配一遍」。本阶段让底层缓冲跨轮复用，内容照旧
每轮重写。

- **`runs` 跨轮复用**：`layoutChildren` 开头 `node.runs = node.runs[:0]`（替代
  `= nil`），`append` 直接接在旧底层数组上，不再从 `nil` grow。函数末尾
  `trimRuns` 释放尾部（`cap` 超出 `len` 且缩得较多时）仍挂着上一轮 `textRun`
  的那段引用——缓冲复用后若不放手，旧文档内容会被旧 `textRun.text` 子串钉在
  内存里。`n==0 || n*4>=cap` 时跳过（缩得不多不值得再走一遍尾部）。
- **行盒缓冲 `curLine` 跨轮复用**：新增 `engine/layout_cache.go`。
  `layoutChildren` 开头 `el.takeLineBuf()` 取上一轮留的缓冲（取走即置 `nil`，
  防 `onChanged`→宿主刷新重入时两次布局共用同一底层数组）；函数末尾
  `el.putLineBuf` 归还。`cap` 超 `maxLineScratch`（4096 项）的不保留——宁可在
  下轮重新 grow，也不让一行的峰值变成整个生命的常驻。
- **`hasTrailingBlank` 零分配**：`[]rune(s)` → `utf8.DecodeLastRuneInString`，
  O(1) 且零分配，口径与旧消毒一致（坏字节同样落到 `U+FFFD`→非空白→false）。
- **结构体字段**：`htmlElement` 新增 `lcache *layoutCache`（指针段末尾，懒分配，
  非行内内容多的元素恒为 `nil`），尺寸不变量 **632B → 640B**（多出的 8B 是一个
  指针，落在含指针段、不产生空洞）；`Clone` 里 `c.lcache = nil`。

同口径对比（无头探针，稳定态单次 `LayoutDocument` 的耗时 / 分配）：

| 场景 | 改前 | 改后 |
|---|---|---|
| 真实 credits 页（19.5MB / 780 `<pre>`） | 503ms / 1762MB | **328ms / 36MB** |
| 单节点 `<p>` 1M 字符（可折行） | 41ms / 161MB | **21ms / 36MB** |
| 单节点 `<pre>` 1M 字符（不折行） | 70ms / 379MB | **52ms / 257MB** |

真实 credits 页重排分配 **1762 → 36MB（−98%，约 49×）**；重排后常驻堆连续 20
轮稳定在 ~491MB 无增长（`HeapAlloc` 同值）。`<pre>` 不折行的单节点场景收益
有限（一整行几十万项，`curLine` 超上限不保留），留给阶段二「脏标记 + 文本
token 缓存」从根上消除「未变更子树整块重排」。行为口径不变：`examples/ua`、
`examples/notepad` 的 `-dump-svg` 与上一提交逐字节一致（SHA256 全等）。


## 字节游标零分配切词（阶段二）：重排分配 36 → 10.9MB

阶段一之后 CPU profile 里 `slicerunetostring`+`encoderune` 合计约 31%——
`addPreText` 每轮把 pre/pre-wrap 文本逐 token `[]rune` 累加再 `string(word)`
编码一遍，同一段 19.5MB 文本每次重排都要重新走一遍。本阶段把 `word []rune`
改成**字节区间**（`wordStart` 起点 + 落位时切 `raw[start:end]` 原语料子串），
纯 ASCII 词不再新建字符串：

- **ASCII 词零分配**：`addPreText` 循环 `for i < len(raw)` 按字节游标扫描；
  ASCII 只记 `wordStart`，换行/空格/制表/CJK 边界时 `raw[wordStart:i]` 切片即
  得 token。制表位固定 8 空格用包级 `preTabSpaces`（`strings.Repeat` 只算一次）。
- **词内 `\r` 口径不变**：旧实现把词内的 `\r` **丢弃**（不入词、不算换行，
  CRLF 归一在解析层做）。字节版本罕见路径用 `wordCR` 记录再拼一次，常见路径
  仍是零分配切片。新增 `engine/whitespace_pre_test.go` 的
  `TestPreTokenizationEdgeCases` 锁死这条口径（词内 CR 接成一个词、CR 在词与
  空格之间拆开、非法 UTF-8 落 `U+FFFD`、CJK 逐字）。
- **尝试过的更优方案已被否决**：全局「token 度量备忘」（进程级 `sync.Map`，
  键 = Graphics+token+字体，跳过后端 `MeasureText`/`FontMetrics`）实测**更慢**
  ——credits **328 → 727ms**、pre 1M **52 → 78ms**、p 1M **21 → 40ms**。单 token
  的 `sync.Map` 查询（可比较 struct 键）比 `FakeGraphics` 的估算度量还贵，而
  credits 页 450 万 token 的查询次数压过了省下的度量次数。已完全回退。

同口径对比（无头探针，稳定态单次 `LayoutDocument` 的耗时 / 分配，阶段二列）：

| 场景 | 阶段一（688c360） | 阶段二 |
|---|---|---|
| 真实 credits 页（19.5MB / 780 `<pre>`） | 328ms / 36MB | **250ms / 10.9MB** |
| 单节点 `<p>` 1M 字符（可折行） | 21ms / 36MB | 21.8ms / 35.5MB |
| 单节点 `<pre>` 1M 字符（不折行） | 52ms / 257MB | 49ms / 255.6MB |

credits 页稳定态重排 **328 → 250ms（−24%）**、分配 **36 → 10.9MB（−70%）**；
`<pre>` 不折行的单节点场景分配不变（一整行几十万项，`curLine` 超上限不保留，
是该场景自身的账）。`<p>` 可折行路径不走 `addPreText`（走 `tokenizeText`），
不受影响。行为口径不变：`examples/ua`、`examples/notepad` 的 `-dump-svg` 与
`688c360` 基线逐字节一致（SHA256 全等）。


## 收敛旁路 + 发射指针化（阶段二后续）：重排 250 → 231ms

改完切词再看 profile，`flushLine`（行盒落位）成了头号热点（38% flat），而它耗时
的大头对纯文本页来说是**白做的两趟扫描**：

- **vertical-align 两轮收敛加旁路**：`flushLine` 会为 `vertical-align: top/bottom`
  的原子盒迭代两轮收敛，但**每行都跑**，哪怕整行一个这样的盒都没有。跳过是严格
  等价的：没有 top/bottom 项时循环既不改动任何项，第二趟重算的 `leadAsc/leadDesc`
  最大值也必然等于 `lineAsc/lineDesc`（各项落位时已逐项累加进去，`asc/desc` 又取
  过 strut 的最大）。用 `layoutChildren` 的局部标记 `lineHasVAlign` 旁路整趟——
  置位在 `addItem` 的 `append` **之后**（软换行会先调一次 `flushLine` 把标记清掉，
  放前面就漏掉「换行后紧跟的这项」），`flushLine` 末尾随 `curLine` 一起清零。
- **发射循环按索引取指针**：行盒落位循环原来是 `for _, it := range curLine`，每
  项整体拷贝一份 120B 的 `lineItem`；credits 页 450 万项就是每次重排约 540MB 的
  纯拷贝流量。改成 `for i := range curLine { it := &curLine[i] }`，收敛循环里的
  第二趟同样改掉。
- 本轮**没有新增结构体字段**（`lineHasVAlign` 是局部变量），`htmlElement` 的 640B
  尺寸不变量不受影响。

同口径对比（无头探针，稳定态单次 `LayoutDocument` 的耗时 / 分配）：

| 场景 | 阶段二（e119bfd） | + 收敛旁路 & 指针化 |
|---|---|---|
| 真实 credits 页（19.5MB / 780 `<pre>`） | 250ms / 10.9MB | **230.8ms / 10.9MB** |
| 单节点 `<p>` 1M 字符（可折行） | 21.8ms / 35.5MB | **17.3ms / 35.5MB** |
| 单节点 `<pre>` 1M 字符（不折行） | 49ms / 255.6MB | **41.7ms / 255.6MB** |

credits 页累计 **503 → 230.8ms（−54%）**、分配 **1762 → 10.9MB（−99.4%）**。
剩下的 profile 大头是 `addPreToken`（38.7% flat）——每 token 一次度量加一条 run
的固有条目开销，不再是可跳过的空转。`vertical_align_test.go` 的 top/bottom/middle
/超上下标用例全绿；行为口径不变：`examples/ua`、`examples/notepad` 的 `-dump-svg`
与 `688c360` 基线逐字节一致（SHA256 全等）。


## 就地写槽位（阶段二后续二）：重排 231 → 188ms

`go tool pprof -list` 出行级 profile 后，两处热点都是同一个形状——「先在栈上
构造结构体、再整份拷进切片」：

| 位置 | 结构体 | 该行列的 flat |
|---|---|---|
| `addPreToken` 的 `append(curLine, lineItem{...})` | 120B | 270ms / 该函数 430ms 的 62% |
| `flushLine` 落位的 `append(runs, textRun{...})` | 56B | 210ms / 该函数 270ms 的 71% |

`append` 带结构体字面量时编译器不能就地构造：先在栈上写一份（含零初始化），
再 memmove 进底层数组，每 token 两趟写内存。全页 450 万 token 就是约 1GB 的
纯搬运。改成**先预留槽位、再逐字段写进去**：

```go
if len(curLine) < cap(curLine) {
    curLine = curLine[:len(curLine)+1]
} else {
    curLine = append(curLine, lineItem{}) // 只为拿到扩容
}
it := &curLine[len(curLine)-1]
it.tn, it.el, it.token = tn, nil, tok
it.x, it.y, it.w = cursorX, cursorY, w
// ……全部字段都要写
```

- **必须写全每一个字段**：`curLine`/`runs` 的底层数组跨轮复用（阶段一），槽位里
  留着上一轮的值，漏一个字段就是读到旧 token / 旧坐标。
- **`*slot = lineItem{...}` 的写法更慢**：试过把它包成 `pushLineSlot()` 返回指针、
  调用方写一个结构体字面量（没写到的字段自动零值，将来加字段不会漏）——实测
  credits **197 → 215ms**，编译器仍按「栈上构造 + 整份拷贝」处理，等于没省。
  所以保留逐字段写法，并在代码注释里写明这个坑。
- **不抽成闭包**：`pushLineSlot` 作为闭包会让 `curLine` 的扩容写回跨函数边界，
  内联不进去；就地写判断反而更快。
- 只改「怎么写」，不改「写什么」：值与改前逐项相同，所以 SVG 仍逐字节一致。

同口径对比（无头探针，稳定态单次 `LayoutDocument` 的耗时 / 分配）：

| 场景 | 收敛旁路+指针化 | + 就地写槽位 |
|---|---|---|
| 真实 credits 页（19.5MB / 780 `<pre>`） | 230.8ms / 10.9MB | **187.8ms / 10.9MB** |
| 单节点 `<p>` 1M 字符（可折行） | 17.3ms / 35.5MB | **16.5ms / 35.5MB** |
| 单节点 `<pre>` 1M 字符（不折行） | 41.7ms / 255.6MB | **42ms / 255.6MB** |

credits 页累计 **503 → 187.8ms（−63%）**、分配 **1762 → 10.9MB（−99.4%）**。
`<pre>` 不折行的单节点场景在噪声内——那 255MB 的账是 `curLine` 超过
`maxLineScratch`（4096 项）不保留、每轮重新 grow，与写入方式无关。

## `<p>` 分词零分配（阶段二后续三）：`<p>` 1M 字符 35.5MB → 0

`-alloc_objects` profile 显示，`<p>`（可折行，走 `tokenizeText`）路径剩余分配
**99.13% 集中在 `tokenizeText`**：单轮 173,434 次，正好是词数。原实现用
`[]rune` 累加每个词、`flush` 时 `string(cur)` 新建一份字符串，另有一份
`[]string` 词表在 grow；而 ASCII 词本就是源串里一段连续字节，直接切子串即可：

| 位置 | 原写法 | 每词分配 |
|---|---|---|
| `flush()` | `out = append(out, string(cur))` | 1 次（词长） |
| 词表 | `var out []string` 1.25× grow | 摊还少量 |

改成**回调形态 + 字节子串**：`tokenizeText(s string, emit func(tok string))`，
保留 `for i, r := range s`（`range` 直接给出 rune 的字节下标），ASCII 词记
`wordStart`、遇边界 `emit(s[wordStart:i])`，零分配出词：

- **不再攒 `[]rune`/`[]string`**：边扫边发，省掉词表增长与 `string(cur)` 复制。
- **CJK 仍按单字 `string(r)` 发射**：与原口径逐字节一致（含坏字节归一为
  `U+FFFD`），本就是原行为、不是分配热点，未改动。
- **token 生命周期**：ASCII 词是 `s` 的字节子串，调用方须在持有 `raw`
  （= `textNode.Text()`，文本节点自身常驻的 `node.text`）期间消费/存储 token。
  `lineItem.token` / `textRun.text` 存的就是词本身那段子串（`r.text = it.token`），
  只钉住该词，不会连带整份文档。
- **两个调用点**（pre-line 路径与 normal 路径）改为传闭包；原「词表非空才先
  `flushPendingSpace()`」用 `flushed` 标志在回调**首次触发**时落位，顺序与旧版
  一致（否则空格宽度被计入游标 → "不接收" 渲染成 "不 接收"）。

同口径对比（无头探针，稳定态单次 `LayoutDocument` 的耗时 / 分配）：

| 场景 | 就地写槽位 | + `tokenizeText` 零分配 |
|---|---|---|
| 单节点 `<p>` 1M 字符（可折行） | 16.5ms / 35.5MB | **12.8ms / ≈0MB（2KB）** |
| 真实 credits 页（19.5MB / 780 `<pre>`） | 187.8ms / 10.9MB | 187.8ms / 10.9MB（不变） |
| 单节点 `<pre>` 1M 字符（不折行） | 42ms / 255.6MB | 42ms / 255.6MB（不变） |

credits 页 780 个 `<pre>`、0 个 `<p>`，`<pre>` 走 `addPreText`，后两行都不经过
`tokenizeText`，口径不变（实测在噪声内）。改后 `<p>` 路径**每轮分配从 35.5MB 降到
2,056 字节**（−99.994%）。正确性由两件事钉住：与旧实现（原样拷贝为 `tokenizeReference`）做**固定语料 +
5 万条随机串**差分（含各类空白、CJK、多字节、非法字节），分词结果逐项全等
（`TestTokenizeTextMatchesReference`；一次性独立脚本另跑过 20 万条，差异 0 条）；
`AllocsPerRun` 锁定纯 ASCII 路径 **0 分配/轮**（`TestTokenizeTextASCIIZeroAlloc`）。
SVG 口径不变：`examples/ua`、`examples/notepad` 的 `-dump-svg` 与 `688c360` 基线
逐字节一致（SHA256 全等）。


## 文本项直接落 `runs`，行盒不再暂存（阶段二后续四）：pre 1M 字符 257MB → 2.6KB

阶段一把行盒累加缓冲 `curLine` 做了跨轮复用，但它的**增长**照旧：不折行的行
（`white-space:pre`、`nowrap`）一行几十万项，每轮都要从空缓冲重新 grow。
`maxLineScratch` 只留下 4096 项以内的那份（见 `layout_cache.go` 的取舍：留
64k 项只换到 <10% 的时间，却按每个容器 ~8MB 常驻），而单节点 `<pre>` 1M 字符
一行就有约 40 万项，**回回都超上限、回回从零 grow**，实测每轮 255.6MB 分配。

根因是文本项本不必在 `curLine` 里过一道：它最终就是写进所属文本节点的
`runs` 的一项。本阶段让 `layoutChildren` 的文本路径**落位即写 run**：

- **文本项直写 `runs`**：`addTextRun` 直接把 token、x、宽、ascent 写进
  `tn.node.runs` 尾部（同「就地写槽位」的手法，零中间结构）；`flushPendingSpace`
  里的间隙空格、`addPreToken`、`tokenizeText` 的两个回调全走它。`curLine`
  此后**只装原子盒**（行内元素的图元盒），文本行不再 grow 任何暂存缓冲。
- **y 落 provisional，行尾按段平移**：基线要等整行排完才知道，故文本项的
  y 先落**游标**值 `cursorY`；`flushLine` 按整行常量补
  `±(asc + baselineAdjust)`（`asc` = 行盒 ascent），x 补 `text-align` 的
  `dx`。同一行的文本项增量完全一致，于是「逐项暂存、逐项回算」退化成
  **按区间批量相加**——被平移的区间记在新增的段表 `lineSegs`
  （`lineRunSeg{tn, start, end}`）里，每轮每节点通常只一段，平移只回读
  `x`/`y`/`asc` 三个字段。
- **`lineCount` 代替 `len(curLine)` 判「本行有无内容」**：软换行的
  `lineCount > 0` 守卫、空行/struts 判定、`<button>` 内容居中的 `dy` 都改用它
  ——文本项已不进 `curLine`，再按长度判会把整行误当空行。
- **`vertical-align: top/bottom` 的收敛以 `asc/desc` 初值为底**：文本项与
  strut 的贡献在落位时已并进 `lineAsc/lineDesc`，收敛循环只遍历 `curLine`
  里剩下的原子盒，每轮从「当前 asc/desc」追加盒贡献，不再重新对整个
  `curLine` 取 max（那会把文本与 strut 的贡献丢掉）。
- **`breakPreLine` 之后重置 `lastInline`**：pre / pre-line 的源换行是硬断行，
  下一行的盒不该接着上一行算盒顶。

同口径对比（无头探针，稳定态单次 `LayoutDocument` 的耗时 / 分配；基线
`688c360`）：

| 场景 | 基线 `688c360` | 阶段二后续四 |
|---|---|---|
| 真实 credits 页（19.5MB / 780 `<pre>`） | 327.6ms / 35.95MB | **178~190ms / 10.75~10.86MB** |
| 单节点 `<p>` 1M 字符（可折行） | 21.0ms / 35.51MB | **9.4~12.4ms / 2,054~2,102 字节** |
| 单节点 `<pre>` 1M 字符（不折行） | **52.1ms / 257.14MB** | **7.8~10.3ms / 2,654~2,681 字节** |

`<pre>` 不折行的 257MB 账正是上面的 `curLine`：一行 40 万项、`lineItem`
112B，每轮从零 grow 到 1.25× 倍率，峰值约两份 45MB 的项缓冲，摊还下来 257MB。
本阶段文本项不再进 `curLine`，这笔账**整笔消失**——同一场景从 257MB 降到
**2.6KB**（−99.999%），耗时 52.1 → 7.8ms。credits 页 35.95 → 10.86MB 是三个
阶段叠加的结果（`runs` 跨轮复用 + 分词零分配 + 文本项不再暂存）；本阶段在
credits 上单独贡献的是每行 `curLine` 的 grow 与常驻（折行后每行十几项，
grow 的摊还本就小，常驻那份 ≤4096 项）。
`<p>` 1M 从 35.51MB 到 2KB 是阶段二分词零分配的成果（见上一节），本轮在这个
场景上的增量落在噪声内。

正确性：

- `go build ./...`、`go vet ./...`、`go test ./... -count=1` 全绿。
- SVG 口径**逐字节**不变：`examples/ua`、`examples/notepad` 的 `-dump-svg`
  与 `688c360` 基线 SHA256 全等（`4a8d8a66…` / `364df932…`）。
- 稳定态常驻堆：`HeapAlloc` 打开后与重排后相等（credits 459.7 → 459.7MB，
  `<pre>`/`<p>` 1M 26.0 → 26.0MB），重排不再净分配任何东西。
- 回归面：`vertical-align` top/bottom/middle/super/sub/text-top/text-bottom/
  长度/百分比全套、`<button>` 内容垂直居中、`<p>`/`<pre>`/预格式空白/列表
  标记/表格/级联样式共享等既有像素与几何断言全过。

## 内存：差异在原生侧，不在引擎侧


- **引擎侧（Go）两条路径完全一样**：堆常驻 ~3MB、每帧分配 216~327KB
  （布局/样式/文本片段/精灵像素与渲染路径无关）。
- **原生侧不同**：
  - 软件路径：目标缓冲 + 纹理都在**系统内存**（共享、可换页到页面文件）；
  - 加速路径：纹理与交换链在**显存**（**独占、不可换页的硬上限池**，桌面
    合成器与浏览器先占一大块）。
- 纹理上传后 CPU 侧就释放了（`sdlFreeSurface`），所以**系统内存反而可能
  更少**；总占用（系统 + 显存）更多。显存用尽的代价也完全不同：系统内存
  超了是变慢（可换页），显存超了是分配失败/渲染出错。

## 选型

| 场景 | 建议 | 依据 |
|---|---|---|
| ≤1080p、静态为主 | 软件够用 | 真实工作 2.1~4.9ms（入队+填充拷贝），60fps 预算 16.6ms 里有 3 倍以上余量 |
| 4K+ / 大图 / 大量半透明 | 加速路径 | 软件路径的「填充+拷贝」4K 已到 4.40ms，且其中约 2.1ms 是躲不掉的整屏 blit（见上一节的上限分析）——面积越大这笔越贵，与页面轻重无关；加速路径的 CPU 侧只花 1.1ms（填充在 GPU 上异步完成） |
| 频繁截图回读 | 软件更简单 | 加速路径要等 GPU 排空队列（stall） |
| 虚拟机 / 无 GPU | 软件（默认） | 本来就不尝试 GPU；只有显式 `GHROMEX_GPU=1` 才创建加速路径（创建失败自动回退软件） |
| 显存紧张的机器 | 软件 | 纹理与交换链都进系统内存 |
| 电池 / 功耗 | **需实测** | 软件路径把填充与拷贝全压在 CPU 上（2~6ms/帧），功耗未必低于唤醒独显 + 等 vsync，取决于电源策略与驱动 |
